# 浏览器安全之「请求劫持」深度解析

## 一、概念界定：什么是请求劫持

请求劫持（Request Hijacking）是指攻击者在浏览器发出请求到服务器处理请求的链路中，通过篡改寻址、拦截传输、伪造身份或欺骗用户交互等手段，使请求偏离预期目标或被注入恶意内容的一类攻击总称。

在浏览器安全语境下，"请求劫持"并非单一攻击，而是一个**攻击家族**，按 OSI 协议栈自底向上可分为三大类：

| 层级 | 攻击类型 | 核心动作 | 典型代表 |
| --- | --- | --- | --- |
| 域名解析层 | DNS 劫持 | 篡改域名→IP 的映射 | 本地 DNS 投毒、运营商强制解析 |
| 传输/应用层 | HTTP 劫持（中间人攻击） | 拦截并篡改 HTTP 报文 | SSL Stripping、ARP 欺骗 + 明文篡改 |
| 浏览器/客户端层 | 客户端请求劫持 | 借用户身份或交互伪造请求 | CSRF、点击劫持（Clickjacking） |



## 二、DNS 劫持（域名解析层）

### 2.1 原理

DNS 的职责是把域名（如 `www.example.com`）翻译成 IP 地址。正常解析流程是：客户端 → 本地 DNS（运营商）→ 根 → 顶级域 → 权威 DNS。

**DNS 劫持**就是攻击者在这条解析链路上篡改响应，把合法域名映射到攻击者控制的虚假 IP，使用户浏览器实际连上恶意服务器，却以为自己在访问正常网站。

### 2.2 常见手段

1. **本地劫持**：篡改用户设备的 `hosts` 文件、路由器 DNS 设置，或植入恶意软件直接修改系统 DNS。
2. **DNS 缓存投毒（Cache Poisoning）**：向递归解析器注入伪造的 DNS 响应，让缓存中存放错误的 IP。
3. **运营商/链路劫持**：运营商在本地 DNS 上动手脚，对特定域名返回广告页或缓存服务器 IP（国内常见的"输入京东跳淘宝"现象）。
4. **中间人篡改 DNS 响应**：在公共 Wi-Fi 等环境中拦截 UDP 53 端口的 DNS 查询并返回伪造结果。

### 2.3 危害

- 钓鱼：用户在仿冒页面输入账号密码。
- 流量劫持：广告注入、恶意脚本下发。
- 完全不可达：拒绝服务。

## 三、HTTP 劫持 / 中间人攻击（传输层，核心考点）

### 3.1 为什么 HTTP 可以被劫持

HTTP 是**明文传输**，存在三大固有风险：

- **窃听风险**：链路上任意节点都能读取通信内容。
- **篡改风险**：可任意修改请求/响应体（如植入广告、注入恶意 JS）。
- **冒充风险**：可伪装成目标服务器与客户端通信。

只要攻击者能在链路上充当"中间人"（如公共 Wi-Fi 的 ARP 欺骗、恶意代理、运营商网关），就能完成劫持。

### 3.2 中间人攻击（MITM）模型

学术上称为 **Dolev-Yao 攻击者模型**：攻击者可以拦截、修改、阻断、重定向客户端与服务器之间的所有流量。

攻击流程：

```
客户端 ──[明文HTTP请求]──> 攻击者(中间人) ──[转发/篡改]──> 服务器
客户端 <──[篡改后响应]── 攻击者(中间人) <──[原始响应]──── 服务器
```

### 3.3 SSL Stripping（SSL 剥离）

该攻击手段由 Moxie Marlinspike 在 2009 年 Black Hat 大会上提出并发布工具 `sslstrip`。

**攻击前提**：很多网站同时支持 HTTP 和 HTTPS，用户首次访问往往输入 `http://` 或点击 `http://` 链接，服务器返回 301/302 跳转到 `https://`。

**攻击流程**：

1. 用户发起 `http://example.com` 请求（明文）。
2. 中间人拦截该请求，**自己以 HTTPS 身份**向真实服务器请求 `https://example.com`。
3. 真实服务器返回包含 `https://` 链接的页面。
4. 中间人把响应中**所有 `https://` 替换成 `http://`**，再以明文 HTTP 返回给用户。
5. 用户后续所有点击都走明文 HTTP，中间人全程可见可改，包括登录密码。
6. 关键：**浏览器地址栏显示的是正常的 `http://`，没有证书警告**，用户难以察觉。研究表明超过 90% 的用户不会注意到地址栏缺少小锁标识。

**本质**：SSL Stripping 不是破解 TLS，而是**阻止连接升级到 TLS**——利用了"HTTP→HTTPS 跳转发生在明文链路上"这个窗口期。

### 3.4 HTTPS 为什么能防 MITM（但防不住 SSL Stripping 的首次跳转）

HTTPS 在 HTTP 与 TCP 之间加入 SSL/TLS，通过：

- **加密**：握手阶段用非对称加密协商对称密钥，后续通信加密。
- **身份校验**：服务器出示 CA 签发的数字证书，客户端验证证书合法性（有效期、颁发机构信任链）。攻击者没有服务器私钥，无法解密；若伪造证书，客户端会报证书错误。

但 HTTPS 有一个**首次访问漏洞（Bootstrap MITM）**：用户第一次访问某域名时，如果走的是 HTTP，那么"HTTP→HTTPS"的 301 跳转本身是明文的，可被中间人拦截替换。RFC 6797 明确承认了这一漏洞。

## 四、核心防御：HSTS（HTTP Strict Transport Security）

### 4.1 是什么

HSTS 是一个响应头，告诉浏览器：**在指定时间内，该域名只能通过 HTTPS 访问，任何 HTTP 请求都在浏览器本地自动升级为 HTTPS，且不允许用户跳过证书错误。** 

### 4.2 语法与指令

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

| 指令 | 作用 |
| --- | --- |
| `max-age=<秒>` | 浏览器记住该策略的时长，必填。`max-age=0` 可撤销。 |
| `includeSubDomains` | 策略扩展到所有子域名（任意深度）。 |
| `preload` | 申请加入浏览器内置的 HSTS 预加载列表。要求 `max-age≥31536000`（1年）且必须带 `includeSubDomains`。 |

### 4.3 工作机制

1. 用户首次访问 `http://example.com`，服务器 301 跳转到 `https://example.com`。
2. 浏览器发起 HTTPS 请求，服务器在 HTTPS 响应中返回 HSTS 头。
3. 浏览器将 `example.com` 加入本地 HSTS 列表，记住 `max-age`。
4. 之后用户即使输入 `http://login.example.com`（子域），浏览器**在发请求前**就自动把 `http://` 替换为 `https://`，端口 80→443，**根本不发出明文请求**。
5. 若遇到证书错误，浏览器**不允许用户点击"继续访问"**，硬失败。

### 4.4 HSTS 如何防御 SSL Stripping

SSL Stripping 的前提是"浏览器会发出明文 HTTP 请求"。HSTS 让浏览器在本地就完成升级，**明文请求根本不离开浏览器**，中间人无从拦截，跳转也不经过网络。

### 4.5 HSTS 的局限与首次访问问题

HSTS 是 **Trust-on-First-Use（TOFU，首次信任）** 模型：**第一次访问必须是成功的 HTTPS 并收到 HSTS 头，策略才生效**。如果用户第一次访问就被中间人劫持了 HTTP 跳转，HSTS 头永远不会被浏览器收到。

**解决方案：HSTS Preload List**

- 网站主动申请加入由 Google 维护、Chrome/Edge/Firefox/Safari 等所有主流浏览器内置的预加载列表。
- 加入后，浏览器**在出厂时就知道**该域名必须 HTTPS，连第一次明文请求都不会发，彻底消除 Bootstrap MITM。
- 注意：preload 是**不可逆**的（移除需要浏览器版本更新），申请前必须确保全站及所有子域都支持 HTTPS。

### 4.6 HSTS 部署的现实问题

NDSS 2017 的实证研究（对 Alexa Top 1M 和浏览器预加载列表的大规模爬取）发现：

- 大量开发者并未完全理解 HSTS，**多数尝试设置 HSTS 头的站点都存在基础错误**，显著削弱了安全性。
- HSTS 与 Cookie、同源策略存在微妙交互：即使主域设置了 HSTS，若 Cookie 的 `domain` 属性设置过宽，仍可能泄露到未受 HSTS 保护的子域。

> **面试加分点**：能说出 HSTS 是 TOFU 模型、有首次访问问题、preload 解决首次问题、以及子域/Cookie 交互陷阱，说明你不仅背了概念，还理解了工程细节。

## 五、DNS 劫持的防御：DNSSEC + DoH/DoT

### 5.1 DNSSEC（DNS Security Extensions）

- **原理**：为 DNS 记录添加数字签名（RRSIG），解析器通过从根域逐级下发的信任链验证响应的真实性和完整性。一旦响应被篡改，签名验证失败，解析器拒绝使用。
- **关键点**：DNSSEC **只保证真实性和完整性，不加密查询内容**——观察者仍能看到你查了什么域名，但无法篡改结果。
- 信任链：根域 → 顶级域 → 权威域，逐级签名验证。

### 5.2 DoH / DoT（加密 DNS 传输）

| 协议 | 全称 | 端口 | 特点 |
| --- | --- | --- | --- |
| **DoH** | DNS over HTTPS | 443 | DNS 查询封装在 HTTPS 报文中，与普通网页流量混在一起，难以被运营商识别和劫持。RFC 8484 标准化。 |
| **DoT** | DNS over TLS | 853 | DNS 查询用 TLS 加密，流量特征明显（固定端口），但延迟更低。 |

DNSSEC 验证"响应是否来自合法权威服务器"，DoH/DoT 保证"查询过程不被窃听篡改"，两者互补而非替代。

### 5.3 其他实用手段

- 手动配置可信公共 DNS（如 1.1.1.1、8.8.8.8、223.5.5.5），绕过被劫持的运营商本地 DNS。
- 定期检查 `hosts` 文件和路由器 DNS 设置。
- 敏感操作避免使用公共 Wi-Fi。

## 六、客户端层请求劫持辨析（CSRF / 点击劫持）

### 6.1 CSRF（跨站请求伪造）

- **原理**：攻击者诱导已登录用户访问恶意页面，恶意页面自动向目标站点发起请求（如 `<img src="https://bank.com/transfer?to=hacker">`），浏览器自动携带目标站点的 Cookie，服务器误以为是用户主动操作。
- **与 HTTP 劫持的区别**：CSRF 不拦截或篡改链路，而是**借用户的浏览器和 Cookie 身份**凭空发起请求；HTTP 劫持是在链路上篡改已有请求。
- **防御**：CSRF Token、`SameSite=Strict/Lax` Cookie、校验 Referer/Origin、敏感操作二次验证。

### 6.2 点击劫持（Clickjacking / UI 重定向攻击）

- **原理**：攻击者用透明 `<iframe>` 把目标网站（如"确认转账"按钮）嵌套在恶意页面上，覆盖在一个诱导性按钮（如"领取奖品"）之上，用户点击时实际点的是 iframe 里的敏感操作。
- **防御（OWASP 标准）**：
  1. `X-Frame-Options: DENY/SAMEORIGIN`（基础防御）。
  2. CSP `frame-ancestors` 指令（更灵活，推荐优先）。
  3. `SameSite` Cookie 属性（页面被 iframe 加载时不携带会话 Cookie）。
  4. JavaScript frame-buster（辅助，不单独依赖）。

## 七、防御体系总览（面试答题框架）

按**分层纵深防御**模型对请求劫持防御模型进行组织：

```
┌─────────────────────────────────────────────┐
│  应用层：CSP / X-Frame-Options / CSRF Token  │  ← 防客户端劫持
├─────────────────────────────────────────────┤
│  传输层：全站 HTTPS + HSTS(+preload)         │  ← 防 HTTP 劫持/SSL Stripping
├─────────────────────────────────────────────┤
│  解析层：DNSSEC + DoH/DoT + 可信公共 DNS     │  ← 防 DNS 劫持
├─────────────────────────────────────────────┤
│  终端层：检查 hosts/路由器、避免公共 Wi-Fi     │  ← 防本地劫持
└─────────────────────────────────────────────┘
```

**关键配置清单**：

```
# 强制 HTTPS，防 SSL Stripping
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload

# 防点击劫持
Content-Security-Policy: frame-ancestors 'self'
X-Frame-Options: SAMEORIGIN

# 防 XSS 注入（注入的脚本可发起任意请求）
Content-Security-Policy: default-src 'self'; script-src 'self'

# Cookie 安全属性（防 CSRF + 防泄露）
Set-Cookie: session=xxx; HttpOnly; Secure; SameSite=Lax 
```

## 面试总结

**Q1：HTTPS 已经加密了，为什么还需要 HSTS？**
A：HTTPS 只保护已经建立的 TLS 连接，但用户首次访问或输入 `http://` 时，"HTTP→HTTPS"的 301 跳转走明文，可被 SSL Stripping 拦截。HSTS 让浏览器本地直接升级，明文请求根本不发出，填补了这个窗口期。

**Q2：HSTS 的 `max-age` 设多大合适？设错了怎么办？**
A：建议从短（如 5 分钟）开始灰度，确认全站 HTTPS 无问题后逐步加长到 1 年（`31536000`）以上。若误设导致站点无法访问，可通过 HTTPS 响应返回 `max-age=0` 撤销——但注意**只能通过 HTTPS 撤销**，HTTP 上的 HSTS 头会被浏览器忽略（防止中间人提前过期）。

**Q3：HSTS preload 有什么风险？**
A：一旦加入浏览器内置列表，移除需要等待浏览器版本更新（可能数月），期间如果你的某个子域不支持 HTTPS，该子域将完全无法访问。所以申请前必须确保**所有子域**都永久支持 HTTPS。

**Q4：DNSSEC 和 DoH 有什么区别？能互相替代吗？**
A：不能。DNSSEC 保证 DNS 响应的**真实性和完整性**（防篡改），但不加密；DoH/DoT 保证 DNS 查询的**传输加密**（防窃听和链路劫持），但不验证响应是否来自合法权威服务器。理想配置是两者同时使用。

**Q5：CSRF 和 HTTP 劫持有什么本质区别？**
A：HTTP 劫持是**链路上的中间人**篡改真实请求；CSRF 是**在用户浏览器里**借用户身份凭空发起一个伪造请求，链路本身没有被篡改。前者需要控制网络节点，后者只需要诱导用户访问恶意页面。

**Q6：如果攻击者拿到了合法 CA 签发的证书（rogue certificate），HSTS 还有用吗？**
A：HSTS 只强制 HTTPS，不验证证书是否是"正确的那一张"。若攻击者能获得受信任 CA 签发的目标域名证书，仍可实施 MITM。对此的防御是 **HPKP（HTTP Public Key Pinning，公钥固定）**，但 HPKP 因误配置风险极高（可能把站点"砖"掉），目前已被主流浏览器废弃，现代方案是 **Certificate Transparency（证书透明度）** + CA 体系改革。NDSS 论文对 HPKP 的部署错误也有详细实证分析。
