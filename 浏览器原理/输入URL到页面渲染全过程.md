# 输入URL到页面渲染全过程

---

# 浏览器原理：从输入 URL 到页面呈现的完整链路

一次网页访问本质上是「**把一个字符串 URL 翻译成屏幕上的像素**」的过程，可拆为六个阶段。**现代浏览器为了性能，会让多个阶段重叠并行，而非严格串行**

```
URL 解析 → ① DNS 解析 → ② TCP 连接(+TLS) → ③ HTTP 请求
        → ④ 服务器响应 → ⑤ 浏览器解析渲染 → ⑥ 断开/复用连接
```

---

## 一、DNS 解析：把域名翻译成 IP

浏览器只能和 IP 通信，所以第一步要把 `www.example.com` 解析成 `93.184.216.34`。

### 1. 缓存优先的查询顺序

DNS 是「**越近越快**」的分层缓存系统，浏览器按由近及远的顺序查：

1. **浏览器自身 DNS 缓存**（Chrome 可在 `chrome://net-internals/#dns` 查看），缓存时长由响应记录的 **TTL（Time To Live）** 决定，通常几分钟到几小时。
2. **操作系统缓存 + hosts 文件**（Windows 的 DNS Client 服务、Linux 的 nscd/systemd-resolved）。
3. **路由器缓存**。
4. **递归解析器（Recursive Resolver）缓存**——通常是 ISP 或公共 DNS（8.8.8.8 / 1.1.1.1），它也会按 TTL 缓存近期结果。

任何一层命中且未过期，就直接返回，不再向上查询。

### 2. 递归查询 vs 迭代查询

- **客户端 → 递归解析器**：是**递归查询**。客户端只发一次请求,请求目标的真实ip地址，递归解析器负责替它跑完整个流程。
- **递归解析器 → 各级 DNS 服务器**：是**迭代查询**。每一级只返回「下一级该查询谁」，由解析器自己继续查询：

```
递归解析器 ──查询根──→ 根服务器："查询 .com 服务器"
           ──查询.com──→ 顶级域服务器："查询 example.com 的权威服务器"
           ──查询权威──→ 权威服务器："IP 是 93.184.216.34"
```

根服务器全球只有 13 组逻辑根（任播部署了数百台物理机），顶级域服务器管理 `.com/.org/.cn` 等，**权威域名服务器**是唯一存储该域名真实记录的地方。

### 3. 记录类型与现代优化

- **A 记录**：IPv4；**AAAA 记录**：IPv6。
- **HTTPS / SVCB 记录**：现代浏览器会同时请求，可直接拿到服务器支持的 ALPN、IP 提示等，减少后续握手往返。
- **DNS 预解析**：页面里的 `<link rel="dns-prefetch" href="//cdn.example.com">` 让浏览器在需要前提前解析。
- **DoH/DoT**：DNS over HTTPS / TLS，防止中间网络篡改或窥探查询。

## 二、TCP 连接：建立可靠传输通道

拿到 IP 后，浏览器向服务器的**443端口(HTTPS)**或**80端口(HTTP)**发起连接。

### 1. TCP 三次握手

```
Client                                  Server
  │── SYN (seq=x) ───────────────────→│   SYN_SENT
  │←── SYN+ACK (seq=y, ack=x+1) ──────│   SYN_RCVD
  │── ACK (ack=y+1) ─────────────────→│   ESTABLISHED
  │                                   │
  │         双方进入 ESTABLISHED       │
```

- 客户端发 **SYN**（同步序列号，携带随机初始序号 `x`）。
- 服务器回 **SYN+ACK**（自己的初始序号 `y`，并确认 `x+1`）。
- 客户端发 **ACK**（确认 `y+1`），连接建立。

**为什么是三次？** 两次无法让客户端确认服务器的发送能力，也无法防止历史失效的 SYN 被服务器误建连接；四次没必要，因为 SYN 和 ACK 可以合并在一个包里。三次是「**双向确认收发能力**」的最小次数。

### 2. TLS 握手（HTTPS 必走）

TCP 建好后，HTTPS 还要做 TLS 握手来协商密钥、认证服务器身份。这一阶段概括为 **DNS → TCP 三次握手 → TLS 握手** 的串行 RTT 链。

**TLS 1.2** 需要 2-RTT；**TLS 1.3** 把握手压缩到 **1-RTT**，并支持 **0-RTT** 重连（用之前会话的 PSK 在首个包就携带加密应用数据）：

- 客户端 `ClientHello` 一次性携带支持的密钥共享（ECDHE）、候选密码套件、扩展。
- 服务器 `ServerHello` + 证书 + 密钥共享直接完成协商，后续应用数据即可加密传输。
- 服务器身份通过**数字证书 + 数字签名**认证，密钥通过 **ECDHE 前向保密**协商，数据用**对称加密 + AEAD**保证机密性与完整性。



### 3. 更快的替代：QUIC / HTTP/3

QUIC 基于 UDP，把「传输可靠性 + 加密握手」合并，**首次连接 1-RTT、重连 0-RTT**，并解决了 TCP 层的队头阻塞。HTTP/3 直接跑在 QUIC 上，现代浏览器与大厂站点已大规模启用。

## 三、HTTP 请求：浏览器向服务器发送消息

连接就绪后，浏览器构造并发送 HTTP 请求报文。

### 1. 请求报文结构

```
GET /index.html HTTP/1.1        ← 请求行（方法 + 路径 + 版本）
Host: www.example.com           ← 头部
User-Agent: Mozilla/5.0 ...
Accept: text/html,*/*
Accept-Encoding: gzip, br
Cookie: session=abc123
Connection: keep-alive
                                ← 空行
（请求体，GET 通常没有）
```

- **方法**：GET/POST/PUT/DELETE/HEAD/OPTIONS 等。
- **关键头部**：`Host`（虚拟主机必需）、`Accept`（内容协商）、`Accept-Encoding`（压缩）、`Cookie`、`If-Modified-Since`/`If-None-Match`（缓存协商）、`Connection`。



### 2. 并发与队头阻塞

- **HTTP/1.1**：同一域名下浏览器通常开 6 个 TCP 连接并发请求，但**单个连接内请求必须串行**（队头阻塞）。`Connection: keep-alive` 让连接在一次响应后保持打开，后续请求复用，避免反复握手。
- **HTTP/2**：单连接上**多路复用**，多个请求/响应以帧并发传输，解决应用层队头阻塞；还支持头部压缩（HPACK）和服务器推送。
- **HTTP/3**：在 QUIC 流上多路复用，某条流丢包不阻塞其他流，彻底解决传输层队头阻塞。



### 3. 预加载扫描器（Preload Scanner）

这是浏览器的一个关键优化：当主 HTML 解析器被 `<script>` 阻塞时，一个轻量的**预加载扫描器**会提前读取后续字节，发现 `<link>`、`<script>`、`<img>`、字体等高优先级资源并**提前发起下载**，不必等解析器真正走到那里。所以页面里的 CSS/JS/图片往往是「被发现就并发下载」，而不是严格按 HTML 顺序。

## 四、服务器响应：服务器对客户端请求的响应



### 1. 响应报文结构

```
HTTP/1.1 200 OK                  ← 状态行（版本 + 状态码 + 原因短语）
Content-Type: text/html; charset=utf-8
Content-Encoding: gzip
Content-Length: 1234
Cache-Control: max-age=3600
Connection: keep-alive
                                 ← 空行
<!DOCTYPE html>...               ← 响应体
```



### 2. 状态码分类

- **1xx** 信息性（如 100 Continue）
- **2xx** 成功（200 OK、201 Created、204 No Content）
- **3xx** 重定向（301 永久、302 临时、304 Not Modified 协商缓存命中）
- **4xx** 客户端错误（400、401、403、404）
- **5xx** 服务器错误（500、502、503、504）



### 3. 响应处理要点

- **Content-Type** 决定浏览器如何解析 body（`text/html` 走渲染管线，`application/json` 交给 JS）。
- **Content-Encoding: gzip/br**：浏览器先解压再处理。
- **Transfer-Encoding: chunked**：服务器边生成边发，浏览器流式接收，无需预先知道 `Content-Length`。
- **缓存头**：`Cache-Control`/`ETag`/`Last-Modified` 决定强缓存与协商缓存，命中 304 时 body 为空，直接用本地副本。

## 五、浏览器解析渲染：把字节变成像素

这是最复杂的阶段，即 **Critical Rendering Path（关键渲染路径）**。MDN 明确其步骤为：DOM、CSSOM、渲染树、布局、绘制，某些情况下还有合成。

### 1. 字节 → DOM 树（增量解析）

```
字节流 → 字符 → Token → DOM 树
```

HTML 解析器是**增量、容错**的：收到一点解析一点，不必等整个文件下载完。它把 `<div>`、`<p>` 等标记成 token，再构造成 DOM 节点树。HTML 规范甚至定义了对不规范标记的自动修复（如 `<p>` 嵌套 `<div>` 会被自动拆分）。

### 2. CSS → CSSOM 树

CSS 同样经历字节→字符→token→树，产出 **CSSOM（CSS Object Model）**。与 DOM 不同：

- CSSOM 是**只读**的（JS 不能直接改 CSSOM 节点，只能通过操作样式间接影响）。
- **CSS 会阻塞渲染**：在 CSSOM 构建完成前，浏览器不会绘制任何内容（防止「无样式闪烁」FOUC），所以 CSS 要尽早加载、放在 `<head>`。



### 3. JavaScript：阻塞解析器的「特殊公民」

默认情况下，解析器遇到**没有** `defer`**/**`async` **的** `<script>` 会**暂停 DOM 构建**，先下载并执行脚本——因为脚本可能用 `document.write()` 或 DOM 操作改变后续结构，必须保证顺序正确。

- `async`：下载不阻塞，下载完立即执行（执行时仍阻塞），执行顺序不保证。
- `defer`：下载不阻塞，等 DOM 解析完成后、`DOMContentLoaded` 前按顺序执行。
- `<script type="module">`：默认 defer 行为。

> 主线程同时承担 JS 执行和渲染各阶段，所以任何长任务都会同时拖慢交互响应和画面更新——这是现代引擎采用多线程架构（合成线程独立于主线程）的根本原因。



### 4. 渲染树（Render Tree）

DOM（含所有节点，包括 `display:none`）+ CSSOM → **渲染树**，只包含**可见**节
点,以及每个节点对应的 CSSOM 样式信息。**不可见的元素不会被包含在渲染树中**：

- `display:none` 的节点不进入渲染树。
- `visibility:hidden` 或 `opacity:0` 仍在树中（占空间）。
- 伪元素（`::before`）等也会成为渲染树节点。



### 5. 布局（Layout / Reflow）

从渲染树的根节点开始，**递归计算每个节点的精确几何信息**——坐标（x, y）和尺寸（width, height）。这是第一次把「文档流」落到具体像素位置。

- 改变 `width/height/margin/padding/position` 等几何属性会触发**重排（reflow）**，且重排必然伴随重绘。**(重排影响页面的几何属性，即元素的尺寸、位置、结构。重绘会影响页面的视觉外观,即颜色、背景、边框样式、阴影等。)**
- 现代浏览器用**脏位系统 + 批量异步布局**减少重排次数，但读取 `offsetWidth` 等布局属性会强制同步布局（layout thrashing）。



### 6. 绘制（Paint / Rasterize）

把布局阶段算好的每个盒子(样式化的DOM元素)**转换成屏幕上的真实像素**：绘制文字、颜色、边框、阴影、图片、按钮等。绘制按层（layer）进行，产出位图。

### 7. 合成（Composite）

把多个图层的位图(如独立的滚动层、动画层等) **按正确顺序叠合**，交给 GPU 输出到屏幕。`transform`、`opacity` 动画可以只触发合成，不触发布局和绘制，因此非常流畅。

合成是在合成线程上执行的，独立于主线程，因此即使主线程繁忙，合成操作仍能保持流畅

### 8. 帧预算

为保证 60fps 流畅，**每一帧（约 16.6ms）内**必须完成：样式计算 → 布局 → 绘制 → 合成。超过这个预算就会掉帧（jank），滚动和动画卡顿。

## 六、断开连接：四次挥手与长连接



### 1. 现代浏览器默认不断开

HTTP/1.1 默认 `Connection: keep-alive`，响应完成后 TCP 连接**保持打开**，后续同域名请求直接复用，省去 DNS、TCP、TLS 的全部握手开销。浏览器会维护一个连接池，连接空闲超过一定时间（或达到上限）才关闭。

只有显式 `Connection: close`、服务器主动关闭、或空闲超时，才会真正断开。

### 2. TCP 四次挥手

```
Client                                  Server
  │── FIN ───────────────────────────→│   FIN_WAIT_1
  │←── ACK ───────────────────────────│   CLOSE_WAIT
  │   (FIN_WAIT_2)                    │
  │←── FIN ───────────────────────────│   LAST_ACK
  │── ACK ───────────────────────────→│   CLOSED
  │   (TIME_WAIT, 等待 2MSL)            │
```

- 主动关闭方发 FIN，表示无数据请求。
- 被动方先回 ACK，但可能还有数据要发，所以进入 CLOSE_WAIT。
- 被动方发完剩余数据后再发 FIN。
- 主动方回 ACK，进入 **TIME_WAIT**，等待 **2MSL（Maximum Segment Lifetime，报文最大生存时间的两倍）** 后才真正关闭。

**为什么是四次？** 因为 TCP 是全双工，两个方向要分别关闭；被动方的 ACK 和 FIN 不能合并（它可能还有数据要发）。

### 3. TIME_WAIT 的意义

1. **保证最后一个 ACK 能到达**：如果被动方没收到 ACK 会重发 FIN，主动方还在 TIME_WAIT 就能重传 ACK。
2. **让本次连接的所有迟到报文在网络中消亡**，避免被下一个复用相同四元组（源/目的 IP+端口）的连接误收。

高并发服务器上大量 TIME_WAIT 会占用端口，常见优化：开启 `tcp_tw_reuse`（仅客户端、依赖时间戳选项）、扩大端口范围、或直接用长连接从源头减少短连接关闭。

## 面试总结

浏览器原理:从输入 URL 到页面呈现的完整链路

1. 首先，因为浏览器只能和IP通信，所以要对用户输入的url域名解析为IP地址码的形式。DNS中采用分层缓存系统,按照: 浏览器自身 DNS 缓存->操作系统缓存+hosts文件->路由器缓存->递归解析器缓存。任意缓存命中且未过期时，直接返回，不再向上查询。如果本地缓存没有，则需要进行向上查询，客户端会向本地DNS服务器(递归解析器)发起递归查询，本地DNS服务器会向根服务器、顶级域名服务器、权威服务器进行迭代查询。
2. 浏览器得到IP地址后，浏览器会向该ip服务器的 443 端口（HTTPS）或 80 端口（HTTP）发起连接。然后进行TCP三次握手进行可靠连接, TCP连接后HTTPS还要进行TLS 握手来协商密钥、认证服务器身份。
3. 当浏览器和服务器建立连接后,浏览器构造并发送请求报文到服务器，请求报文中有请求行(请求方法+请求路径+协议版本)，请求头(Host,User-Agent)，请求体等内容。

4.服务器进行响应，返回响应报文。报文结构与请求报文类似，响应头中**Content-Type**决定了浏览器如何解析body,**缓存头**：Cache-Control/ETag/Last-Modified决定强缓存与协商缓存，命中 304 时 body 为空，直接用本地副本。

5.浏览器根据报文信息解析渲染响应报文body部分，主要步骤为: 将字节流转变为DOM树 -> CSS转变为CSSOM树 -> (额外步骤：解析执行JS中的`<script>`脚本) -> 将DOM树和CSSOM树合成为渲染树 -> 布局 -> 绘制 -> 合成输出

- 将字节流转变为DOM树: HTML解析器解析进行:字节流->字符->token->DOM树的解析优化处理。
- CSS转变为CSSOM树: CSS 同样经历字节→字符→token→CSSOM树。其中CSSOM树为只读,且会阻塞渲染。
- 额外步骤中，解析器如果遇到了有 `defer`/`async` 的 `<script>`** 会暂停 DOM 构建，先下载并执行脚本内容,防止脚本内容改变DOM结构。
- 将DOM树和CSSOM树合成为渲染树: 将DOM树和CSSOM树合成为渲染树,只包含可见节点
- 布局：计算每个渲染树元素在屏幕上的确切位置和大小，确定所有元素的几何信息。
- 绘制:将渲染树的各个节点转换为屏幕上的像素
- 合成：浏览器将多个图层合并成最终的屏幕图像并输出到屏幕上。
